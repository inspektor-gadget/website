**Which application paths are allocating GPU memory? Is growing memory usage
expected caching, or something to investigate? Do we need another GPU, or
better visibility into the capacity we already have?**

Device metrics alone cannot answer these questions. Inspektor Gadget captures
CUDA allocation call stacks without changing application code, resolves them
into profiles, and adds Kubernetes workload context. Combine those profiles
with allocation/free activity and driver-reported state to investigate what
your workload is doing.

:::note Three complementary views

Profiles show **where allocations originate**; counters show **allocation and
free activity**; gauges show **reported memory and GPU activity**. They measure
different things: do not add or reconcile their totals. Device-wide readings
have no pod ownership; process readings and CUDA observations carry workload
context.

:::

## 1. Prepare the cluster

Use a Kubernetes cluster with working NVIDIA GPU workers and permission to
deploy Inspektor Gadget's privileged DaemonSet.

Check which workers advertise NVIDIA GPU resources:

```bash
kubectl get nodes \
  -o custom-columns='NAME:.metadata.name,GPU:.status.allocatable.nvidia\.com/gpu'
```

## 2. Connect the observability backends

Use your existing **Pyroscope, Prometheus, and Grafana**, or install an
evaluation stack:

```bash
helm repo add grafana https://grafana.github.io/helm-charts
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
```

Create the two values files:

<details>
<summary>pyroscope-values.yaml</summary>

```yaml
architecture:
  microservices:
    enabled: false
  storage:
    v1: false
    v2: true
alloy:
  enabled: false
agent:
  enabled: false
minio:
  enabled: false
pyroscope:
  replicaCount: 1
  image:
    tag: "2.4.3"
  extraArgs:
    log.level: info
  persistence:
    enabled: true
    size: 10Gi
  structuredConfig:
    storage:
      backend: filesystem
```

</details>

<details>
<summary>monitoring-values.yaml</summary>

```yaml
grafana:
  plugins:
    - grafana-pyroscope-app
  additionalDataSources:
    - name: Pyroscope
      uid: local-pyroscope
      type: grafana-pyroscope-datasource

              regex: '(.+)'
              replacement: '$1:2224'
            - sourceLabels: [__meta_kubernetes_pod_ip]
              targetLabel: __address__
              regex: '(.+:.*)'
              replacement: '[$1]:2224'
            - sourceLabels: [__meta_kubernetes_pod_node_name]
              targetLabel: instance
          metricRelabelings:
```

</details>

```bash
helm upgrade --install pyroscope grafana/pyroscope \
  --version 2.4.3 -n monitoring --create-namespace \
  -f pyroscope-values.yaml --wait --timeout 10m
helm upgrade --install monitoring prometheus-community/kube-prometheus-stack \
  --version 92.21.2 -n monitoring --create-namespace \
  -f monitoring-values.yaml --wait --timeout 10m
```

This uses **Pyroscope 2.4.3**, the latest release at the time of writing.
The Pyroscope values deploy one instance with filesystem storage and a 10 GiB
PVC, requiring a default StorageClass. The monitoring values provision
Grafana's Pyroscope data source and a standard Prometheus Operator
`PodMonitor` that scrapes **every Gadget pod** on port `2224`.
These are evaluation settings, not a highly available production deployment.

:::tip Already have observability backends?

For existing backends, skip these installations. Copy the `PodMonitor` under
`extraManifests` into your monitoring configuration, adjusting its namespace
and `release` label to match your Prometheus monitor selectors. Without the
Operator, configure equivalent pod discovery for `k8s-app=gadget` in namespace
`gadget`, keeping the `gadget` container, scraping each pod IP on port `2224`,
and preserving the worker name as `instance`. Do not scrape through a
load-balanced Service.

Add a Pyroscope data source to existing Grafana using its HTTP **query**
endpoint. The collector needs the OTLP profiles **ingestion** endpoint; for
distributed Pyroscope this is the distributor/write endpoint, not the query
frontend.

:::

## 3. Start Inspektor Gadget

Create `inspektor-gadget-values.yaml`:

<details>
<summary>inspektor-gadget-values.yaml</summary>

```yaml
hostPID: true
nodeSelector:
  kubernetes.io/os: linux
bridges:
  gpu:
    enabled: true
    accessMode: toolkit-env
    pollInterval: 100ms
config:
  operator:
    otel-metrics:
      otel-metrics-listen: true
      otel-metrics-listen-address: "0.0.0.0:2224"
    otel-profiles:
      exporters:
        pyroscope-exporter:
          exporter: otlp-grpc
          compression: gzip
          endpoint: pyroscope.monitoring.svc.cluster.local:4040
          insecure: true
  gadgetConfigMaps:
    - name: gpu-memory-profiles
      imageName: ghcr.io/inspektor-gadget/gadget/profile_cuda:v0.58.0
      timeout: 0
      paramValues:
        operator.KubeManager.all-namespaces: "true"
        operator.oci.annotate: "allocs.k8s.podName:profiles.sample-attribute=true,allocs.k8s.namespace:profiles.sample-attribute=true"
        operator.oci.ebpf.collect-otel-stack: "true"
        operator.oci.ebpf.collect-ustack: "true"
        operator.otel-profiles.otel-profiles-exporter: pyroscope-exporter
        operator.otel-profiles.otel-profiles-sanitize-labels: "true"
        operator.ustack.symbolizers: otel-ebpf-profiler
    - name: gpu-memory-metrics
      imageName: ghcr.io/inspektor-gadget/gadget/top_cuda_memory:v0.58.0
      timeout: 0
      paramValues:
        operator.KubeManager.all-namespaces: "true"
        operator.oci.annotate: "libcuda_mem_stats.k8s.podName:metrics.type=key,libcuda_mem_stats.k8s.namespace:metrics.type=key,libcudart_mem_stats.k8s.podName:metrics.type=key,libcudart_mem_stats.k8s.namespace:metrics.type=key"
        operator.otel-metrics.otel-metrics-name: "libcuda_mem_stats:libcuda_mem_stats,libcudart_mem_stats:libcudart_mem_stats"
    - name: gpu-top
      imageName: ghcr.io/inspektor-gadget/gadget/gpu_top:v0.58.0
      timeout: 0
      paramValues:
        operator.oci.annotate: "gpu_top:metrics.collect=true,gpu_top.device:metrics.type=key,gpu_top.sm_util_pct:metrics.type=gauge,gpu_top.mem_util_pct:metrics.type=gauge,gpu_top.mem_used_raw:metrics.type=gauge,gpu_top.mem_total_raw:metrics.type=gauge,gpu_top.pcie_rx_kbps:metrics.type=gauge,gpu_top.pcie_tx_kbps:metrics.type=gauge"
        operator.otel-metrics.otel-metrics-name: "gpu_top:gpu-top"
    - name: gpu-top-per-pid
      imageName: ghcr.io/inspektor-gadget/gadget/gpu_top_per_pid:v0.58.0
      timeout: 0
      paramValues:
        operator.KubeManager.all-namespaces: "true"
        operator.oci.annotate: "gpu_top_per_pid:metrics.collect=true,gpu_top_per_pid.proc.pid:metrics.type=key,gpu_top_per_pid.proc.comm:metrics.type=key,gpu_top_per_pid.k8s.podName:metrics.type=key,gpu_top_per_pid.k8s.namespace:metrics.type=key,gpu_top_per_pid.runtime.containerName:metrics.type=key,gpu_top_per_pid.gpu_device_primary:metrics.type=key,gpu_top_per_pid.mem_used_raw:metrics.type=gauge,gpu_top_per_pid.sm_util_pct_max:metrics.type=gauge,gpu_top_per_pid.mem_util_pct_max:metrics.type=gauge,gpu_top_per_pid.device_count:metrics.type=gauge"
        operator.otel-metrics.otel-metrics-name: "gpu_top_per_pid:gpu-top-per-pid"
```

</details>

The values start `profile_cuda`, `top_cuda_memory`, `gpu_top`, and
`gpu_top_per_pid` continuously on Linux workers. They enable stack collection,
symbolization, and pod/namespace enrichment, then export profiles to Pyroscope
and metrics to Prometheus.

For existing Pyroscope, change
`config.operator.otel-profiles.exporters.pyroscope-exporter.endpoint` to its
ingestion address. The example uses
`pyroscope.monitoring.svc.cluster.local:4040`. Label sanitization is enabled so
Pyroscope 2.x receives sample attributes such as `k8s_podName`,
`k8s_namespace`, and `proc_comm`, matching the metric labels.

:::note Choose the bridge access mode

The bridge uses `toolkit-env` to access NVIDIA telemetry without reserving a
GPU. If your NVIDIA runtime hook does not run for this container, change
`bridges.gpu.accessMode` to `hostpath`; set `runtimeClassName` if your runtime
requires it. Adjust worker tolerations and runtime sockets as needed.

:::

```bash
helm upgrade --install gadget \
  oci://ghcr.io/inspektor-gadget/inspektor-gadget/charts/gadget \
  --version 0.58.0 -n gadget --create-namespace \
  -f inspektor-gadget-values.yaml --wait --timeout 10m

kubectl get pods -n gadget -l k8s-app=gadget -o wide
kubectl get configmaps -n gadget -l type=gadget-instance
```

Expect one ready pod per Linux worker and four instance ConfigMaps.
Inspektor Gadget and its Gadget images use **v0.58.0**, which supports the
current Pyroscope OTLP profiles protocol. Merge the values with your current
configuration if Gadget is already installed.

:::note Keep telemetry private

The example uses cluster-internal endpoints without TLS. Restrict access with
network policies; configure TLS and required access controls for external
backends.

:::

## 4. Explore your workload in the dashboard

:::tip Capture initialization, not just requests

Start or exercise your CUDA workload **after collection starts**. For model
servers, capture initialization as well as requests: model loading and KV-cache
setup can account for much of the allocation volume. Only restart workloads
when it is safe; allocations made before attachment cannot be reconstructed.

:::

For the evaluation stack, open Grafana at `http://localhost:3000`:

```bash
kubectl port-forward -n monitoring svc/monitoring-grafana 3000:80
```

In another terminal, retrieve the generated password and log in as `admin`:

```bash
kubectl get secret -n monitoring monitoring-grafana \
  -o jsonpath='{.data.admin-password}' | base64 --decode; echo
```

### Import the GPU observability dashboard

In Grafana, open **Dashboards -> New -> Import**, paste the JSON below, and
select **Load**, then **Import**. Choose your Prometheus and Pyroscope data
sources in the dashboard's dropdowns, select the CUDA allocation profile type
(`process_cuda`, allocation bytes), and filter by namespace and pod.

The dashboard combines allocation profiles, allocation/free activity, process
memory and utilization, and device-level PCIe throughput. It uses standard
Prometheus and Pyroscope data sources and does not require a cluster label.
Namespace and pod choices come from observed CUDA activity or process metrics.

:::note Device traffic is not workload traffic

The PCIe panel filters devices using the selected namespace and pod's
single-device process readings, matching both node and device index. Its values
remain total device traffic, including other workloads sharing that GPU.
Processes using multiple GPUs report a sentinel primary-device index rather
than a complete device list, so this panel cannot map their devices. Devices
without a matching process reading are not shown.

:::

In this capture, `GPUModelRunner._allocate_kv_cache_tensors` accounts for
approximately **66.3 GiB of allocation volume**. That identifies the allocation
origin, not how much memory remains live.

:::tip Read the allocation flamegraph

A bar's width is **allocated bytes**, not execution time or currently live
memory. **Total** includes child calls; **self** attributes bytes directly to
that function. Look for large self allocations, not just wide parents.
Resolved native and supported language frames depend on stack collection and
symbolization; unknown frames do not establish an application-level cause.

:::
